# Важные ограничения и риски

## Приоритетные наблюдения

| Приоритет | Наблюдение | Влияние | Основание |
|---|---|---|---|
| Высокий | Интернет, Telegram или питание могут стать недоступными | Отправка в срок невозможна; после возвращения будут отчёты о пропусках | `scheduler.py`, `README.md` |
| Средний | Поиск группы/темы зависит от точного и уникального названия | Переименование или дубликат остановят запуск | `control.py` |
| Средний | Отправка себе идёт от того же аккаунта | Пуш для собственных сообщений может не появиться; нужно проверить на устройстве `[ASK USER]` | `scheduler.py`, `README.md` |
| Средний | Старое запланированное сообщение может не сняться | Возможна его доставка старым способом; приложение предупредит | `scheduler.py`: `cancel_legacy_scheduled` |

## Технический долг

- Сроки хранятся локальным временем без зоны; переход часового пояса или летнего времени требует отдельной политики (`db.py`).
- Имя адресата `@username` хранится строкой; смена username может сломать отправку (`commands.py`, `db.py`).
- Автоматической проверки реального Telegram API и CI нет (`tests/`, дерево проекта).

## Безопасность

- Сессия Telethon даёт доступ к аккаунту; `.gitignore` исключает её, README требует хранить её как пароль.
- Команды фильтруются по своему ID, нужному чату и теме (`main.py`, `control.py`).
- Отчёты могут содержать первые 120 символов текста напоминания; тема должна оставаться приватной (`scheduler.py`).

## Производительность и масштабирование

- Используется одно соединение SQLite и один процесс; запуск нескольких экземпляров не поддерживается (`main.py`, `db.py`).
- Цикл просматривает просроченные записи последовательно и делает паузу между несколькими отправками (`scheduler.py`). Замеров нагрузки нет `[TODO]`.
